# v0.5 safe project command execution

## Contract

Post-worker commands are selected from immutable project configuration, not from worker output. `container-required` is the registered-project default. The provider first checks that Docker is reachable and that the configured literal image is already local. It also invokes `docker run --pull never`, so a missing image cannot trigger an implicit download. Missing runtime or image produces `execution_provider_unavailable` and prevents the command from starting.

For post-worker `test`, `typecheck`, `lint`, and `build`, Docker receives one writable bind mount of the managed workspace at `/workspace` plus the nested `<workspace>/.git` bind mount at `/workspace/.git` marked read-only. Missing, symlinked, or non-directory Git metadata fails before the container starts. No other host bind mounts are permitted: no home directory, SSH material, external Git configuration, Codex configuration, orchestration credentials, or Docker socket. The root filesystem is read-only; `/tmp` is a bounded tmpfs. The process runs without a shell, as non-root, with all Linux capabilities dropped, `no-new-privileges`, CPU/memory/PID limits, an execution timeout, and `--network none`.

Bootstrap `install` is the only phase allowed to use the container's default network, and it occurs before the worker. The orchestration flow does not automatically run install after worker output; a package or lockfile modification is a sensitive diff and remains behind the v0.4 approval boundary.

## Explicit fallback and limitation

`container-required` never falls back to the host. `container` may use `local-sanitized` only with the explicit `fallbackProvider` setting. Local-sanitized execution remains shell-free and strips orchestration credentials, but cannot offer Docker-equivalent host filesystem or network isolation; doctor reports that limitation instead of claiming a sandbox.

The controlled commit is `git commit --no-verify`; it is preceded by a fresh validation of the configured branch, HEAD, exact normalized GitHub origin, and repository identity. Push repeats that validation. Origins are accepted only when they are the configured GitHub HTTPS or SSH remote, not merely a string containing the expected owner/repository.

LeadFinder declares a prepared-image contract, `agent-node22-pnpm11:local`, with `pnpm 11.19.0`. The orchestrator will not build, pull, download, or fabricate an image digest. On an operator without Docker, this image is **not operationally verified**; doctor reports image availability separately from that declared toolchain.

The implementation intentionally does not pass a Docker socket into a container and does not use an alternate `DOCKER_HOST`. Docker documentation treats control of the daemon as privileged authority; this boundary is about isolating the project command, not making the daemon available to it.

## Operational evidence

`agent doctor --project <id>` reports configured and selected provider, Docker availability, image availability, image pinning, project toolchain, Git metadata isolation, post-worker network policy, and host fallback. This lets an operator distinguish real container isolation, a deliberate local-sanitized configuration, and a fail-safe unavailable provider before a run is attempted.
